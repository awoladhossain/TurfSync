# System Bottleneck

## ⚠️ Bottleneck #1 — DB Connection Pool

```text
PostgreSQL default: max 100 connections
Prisma default pool: 10 connections
Peak এ 500 req → 490টা queue এ অপেক্ষা করে
→ Latency বেড়ে যায়, timeout হয়
```

### কানেকশন পুল কী? (The Basics)

ডাটাবেসের সাথে কানেক্ট হতে প্রতিবার "নতুন রাস্তা" তৈরি করা অনেক সময়সাপেক্ষ কাজ।

তাই Prisma আগে থেকেই ১০টি রাস্তা (Default Pool) খুলে রাখে।

যখনই আপনার অ্যাপ থেকে কোনো ডাটা দরকার হয়, সে ওই ১০টি রাস্তার যেকোনো একটি ব্যবহার করে এবং কাজ শেষে রাস্তাটি অন্য রিকোয়েস্টের জন্য ছেড়ে দেয়।

### কেন জ্যাম লাগে? (The Peak Time Crisis)

- সীমিত রাস্তা: আপনার হাতে আছে মাত্র ১০টি কানেকশন (Prisma default)।

- হঠাৎ ট্রাফিক: আপনার টার্ফ অ্যাপে পিক আওয়ারে (যেমন শুক্রবারে) একসাথে ৫০০ জন বুকিং করার জন্য রিকোয়েস্ট করলো।

- The Bottleneck: প্রথম ১০ জন ওই ১০টি কানেকশন দখল করে কাজ করবে। বাকি ৪৯০ জনের জন্য কোনো রাস্তা খালি নেই।

### কনসিকুয়েন্স (এর ফলে কী হয়?)

- Queueing (লাইন ধরা): ওই ৪৯০টি রিকোয়েস্ট আপনার মেমরিতে লাইনে দাঁড়িয়ে থাকে।

- High Latency: যেহেতু তারা কানেকশন পাচ্ছে না, তাই ইউজারদের ব্রাউজারে শুধু লোডিং এনিমেশন ঘুরতে থাকে।

- Timeout Error: যদি প্রথম ১০ জনের কাজ শেষ হতে দেরি হয়, তবে লাইনে দাঁড়িয়ে থাকা রিকোয়েস্টগুলো একটি নির্দিষ্ট সময় পর (যেমন ৫-১০ সেকেন্ড) অটোমেটিক "Cancel" হয়ে যায়। ইউজার তখন 504 Gateway Timeout বা Connection Timeout এরর দেখে।

### ৪. PostgreSQL-এর সীমাবদ্ধতা

পোস্টগ্রেস ডাটাবেস নিজে সর্বোচ্চ ১০০টি কানেকশন নিতে পারে।

আপনি যদি ভাবেন প্রিজমার পুল ১০ থেকে বাড়িয়ে ৫০০ করে দেবেন, তবে ডাটাবেস সেটা নিতে পারবে না কারণ তার নিজেরই লিমিট ১০০। সে তখন নিজেই ক্রাশ করবে।

### ৫. সমাধানের পথ (The Pro Way)

- Pool Size টিউনিং: যদি আপনার ডাটাবেস ভালো কনফিগারেশনের হয়, তবে আপনি প্রিজমার কানেকশন লিমিট ১০ থেকে বাড়িয়ে ৩০ বা ৫০ করতে পারেন।

- PgBouncer (The Middleman): এটি সবচেয়ে সেরা সমাধান। এটি ডাটাবেসের সামনে বসে হাজার হাজার ইউজারের কানেকশন রিসিভ করতে পারে এবং সেগুলোকে ম্যানেজ করে ডাটাবেসের কাছে পাঠায়।

- Prisma Accelerate: আপনি যদি ক্লাউড ব্যবহার করেন, তবে প্রিজমার নিজস্ব কানেকশন পুলিং সার্ভিস (Accelerate) ব্যবহার করে এই সমস্যা পুরোপুরি দূর করতে পারেন।

### ৬. আপনার কোডের ওপর প্রভাব

আপনি যখন আপনার Turf Service-এ অনেকগুলো কুয়েরি চালাবেন (যেমন: স্লট জেনারেশন বা বুকিং লিস্ট), তখন যদি কানেকশন পুল ছোট থাকে, তবে সিস্টেমটি অনেক স্লো মনে হবে।

> সহজ কথা: কানেকশন পুল হলো একটি ব্যাংকের ১০টি কাউন্টারের মতো। ৫০০ কাস্টমার আসলে জ্যাম লাগবেই। হয় আপনাকে কাউন্টার বাড়াতে হবে (Limit Increase), অথবা একজন ভালো ম্যানেজার রাখতে হবে (PgBouncer) যে কাস্টমারদের দ্রুত সামলাবে।

প্রিজমা (Prisma) ব্যবহার করে আপনার সুবিধামতো Pool Size বাড়াতে বা কমাতে পারেন। এটি করার জন্য আপনাকে কোডে কোনো পরিবর্তন করতে হবে না, শুধু আপনার .env ফাইলের ডাটাবেস ইউআরএল-এর শেষে একটি প্যারামিটার যোগ করলেই হবে।

### কীভাবে বাড়াবেন? (The Syntax)

আপনার DATABASE_URL এর শেষে connection_limit লিখে আপনি সংখ্যাটি সেট করে দিতে পারেন।

উদাহরণ:

```bash
# ১০ (Default) থেকে বাড়িয়ে ২০ করতে চাইলে:
DATABASE_URL="postgresql://user:password@localhost:5432/mydb?connection_limit=20"
```

### ২. কতটুকু বাড়ানো নিরাপদ?

আপনি চাইলেই ৫০০ বা ১০০০ দিতে পারবেন না। আপনার ডাটাবেস (PostgreSQL) এর একটি নির্দিষ্ট ক্ষমতা আছে।

- PostgreSQL Default Max Connections: সাধারণত ১০০।

- হিসাব: আপনার যদি ৩টি আলাদা মাইক্রোসার্ভিস থাকে এবং প্রত্যেকটিতে connection_limit=40 দেন, তবে মোট হবে ১২০ ($40 \times 3$), যা ১০০-এর বেশি। তখন ডাটাবেস এরর দিবে।

- সেফ জোন: সাধারণত একটি ছোট-মাঝারি প্রজেক্টের জন্য ২০ থেকে ৩০ এর মধ্যে রাখা নিরাপদ।

### ৩. কখন এটি কাজ করবে না? (The Trap)

আপনি যদি Serverless এনভায়রনমেন্টে (যেমন: Vercel বা AWS Lambda) আপনার NestJS অ্যাপটি ডেপ্লয় করেন, তবে এই connection_limit খুব একটা কাজে আসবে না। কারণ:

- সার্ভারলেস সিস্টেমে প্রতিবার রিকোয়েস্ট আসার সময় আপনার অ্যাপের একটি নতুন "Instance" তৈরি হয়।

- যদি ১০০ জন ইউজার আসে, তবে ১০০টি ইন্সট্যান্স তৈরি হবে এবং প্রত্যেকে ১টি করে কানেকশন নিলেও ডাটাবেসের ১০০টি লিমিট শেষ হয়ে যাবে।

- সমাধান: এই ক্ষেত্রে PgBouncer বা Prisma Accelerate ব্যবহার করা ছাড়া উপায় নেই।

### ৪. লিনাক্স বা প্রোডাকশনে চেক করার উপায়

আপনার ডাটাবেস বর্তমানে কয়টি কানেকশন সাপোর্ট করছে তা দেখতে এই SQL কুয়েরিটি চালাতে পারেন:

```bash
SHOW max_connections;
```

## N+1 Query Problem

```text
⚠️ Bottleneck #2 — N+1 Query10 booking list
করলে:1 query bookings + 10 query users+ 10 query turfs = 21 DB calls!
→ Prisma include দিয়ে 1 call এ করা যায়
```

### N+1 Query আসলে কী?

সহজ কথায়, N মানে হলো আপনার মেইন ডাটা (যেমন: ১০টি বুকিং), আর +1 হলো সেই মেইন লিস্ট আনার জন্য করা প্রথম কুয়েরি।

### সমস্যাটি যেভাবে ঘটে:

১. আপনি ডাটাবেসকে বললেন: "সব বুকিং দাও।" (এটি হলো ১টি কুয়েরি)

২. ডাটাবেস ১০টি বুকিং দিল।

৩. এখন আপনার কোড লুপ চালিয়ে প্রতিটি বুকিংয়ের জন্য আলাদাভাবে ইউজার এবং টার্ফের তথ্য খুঁজতে আবার ডাটাবেসে যায়।

- _ ১ম বুকিংয়ের ইউজার কে? (১টি কুয়েরি)

- _ ১ম বুকিংয়ের টার্ফ কোনটি? (১টি কুয়েরি)\* ...

এভাবে ১০টি বুকিংয়ের জন্য ২০টি বাড়তি কুয়েরি।

মোট কুয়েরি: $1 (\text{bookings}) + 10 (\text{users}) + 10 (\text{turfs}) = 21 \text{ DB calls!}$

### ২. সমাধান: Prisma include (Eager Loading)

প্রিজমা আমাদের একটি পাওয়ারফুল অপশন দেয় যার নাম include। এটি SQL-এর JOIN এর মতো কাজ করে। এটি ডাটাবেসকে একবারে বলে দেয় যে, "বুকিং তো আনবা সাথে ওই বুকিংয়ের সাথে যুক্ত ইউজার আর টার্ফের ডাটাও একসাথেই প্যাকেট করে নিয়ে আসো।"

ভুল পদ্ধতি (আগে যা হচ্ছিল):

```js
const bookings = await this.prisma.booking.findMany();
// এরপর লুপ চালিয়ে ইউজার/টার্ফ খুঁজলে N+1 হবে।
```

সঠিক পদ্ধতি (include ব্যবহার করে):

```js
const bookings = await this.prisma.booking.findMany({
  include: {
    user: true, // বুকিংয়ের সাথে ইউজার ডাটাও নিয়ে আসবে
    turf: true, // বুকিংয়ের সাথে টার্ফ ডাটাও নিয়ে আসবে
  },
});
```

### কেন এটি গেম চেঞ্জার?

| বিষয় | N+1 পদ্ধতি (আগের) | include পদ্ধতি (বর্তমান) |
| --- | --- | --- |
| DB Calls | ডাটা বাড়লে কল বাড়তে থাকে (২১, ১০১, ১০০১...) | ডাটা যত খুশি হোক, কল হবে মাত্র ১টি। |
| Latency | অনেকগুলো কল হওয়ায় নেটওয়ার্ক ডিলে বেড়ে যায়। | একবারে সব ডাটা আসায় অনেক ফাস্ট। |
| DB Pressure | ডাটাবেস বারবার কানেকশন হ্যান্ডেল করতে গিয়ে হাঁপিয়ে ওঠে। | ডাটাবেসের ওপর চাপ অনেক কম। |

## Slot Availability

```text
⚠️ Bottleneck #3 — Slot Availability
500 user একসাথে slot দেখতে আসলে
→ 500 DB query একসাথে
Redis cache না থাকলে DB মরে যায়
Solution: Cache + cache invalidation strategy
```

### ১. সমস্যা: কেন ডাটাবেস "মরে যায়"? (The Problem)

ইউজার যখন অ্যাপ ওপেন করে, সে প্রথমেই দেখে "কোন কোন স্লট খালি আছে?"।

ধরি, আপনার ১টি টার্ফের দিনে ১৫টি স্লট আছে।

৫০০ জন ইউজার একসাথে অ্যাপে ঢুকলে ডাটাবেসে ৫০০টি বড় SELECT কুয়েরি যাবে।

ডাটাবেসকে প্রতিবার ডিস্ক থেকে ডাটা খুঁজে ক্যালকুলেশন করে রেজাল্ট দিতে হয়।

ফলাফল: ডাটাবেসের CPU ১০০% হয়ে যাবে, কানেকশন পুল শেষ হয়ে যাবে এবং নতুন কেউ বুকিং করতে পারবে না।

### ২. সমাধান: Redis Cache (The Fast Lane)

রেডিস হলো একটি ইন-মেমোরি ডাটাবেস। এটি ডাটা ডিস্কে না রেখে RAM-এ রাখে, তাই এটি ডাটাবেসের চেয়ে ১০০ গুণ বেশি দ্রুত।

কাজের ধারা:

১. ১ম ইউজার যখন স্লট দেখতে চাবে, সিস্টেম ডাটাবেস থেকে ডাটা এনে রেডিসে একটি Key হিসেবে সেভ করে রাখবে (যেমন: slots:turf_1:2026-05-10)।

২. পরবর্তী ৪৯৯ জন ইউজার যখন আসবে, সিস্টেম আর ডাটাবেসে যাবে না। সে সরাসরি রেডিস থেকে ডাটা দিয়ে দিবে।

৩. ডাটাবেস এখন একদম রিল্যাক্সড থাকবে কারণ তাকে আর ৫০০ বার একই কাজ করতে হচ্ছে না।

### ৩. চ্যালেঞ্জ: Cache Invalidation (ডাটা কখন মুছবেন?)

ক্যাশিংয়ের সবচেয়ে কঠিন কাজ হলো Invalidation। ধরুন, আপনি স্লট লিস্ট ক্যাশ করে রেখেছেন যেখানে দেখাচ্ছে "সকাল ১০টার স্লট খালি"। কিন্তু এর মধ্যে একজন ইউজার ওই স্লটটি বুক করে ফেলেছে।

এখন যদি আপনি ক্যাশ আপডেট না করেন, তবে অন্য ইউজাররা এখনো স্লটটি "খালি" দেখবে এবং ক্লিক করে এরর খাবে। এটাকে বলে Stale Data।

কৌশল (Strategies):

- Write-Through Cache: যখনই কেউ বুকিং করবে (DB update), সাথে সাথে ওই টার্ফের স্লট ক্যাশটি রেডিস থেকে ডিলিট বা আপডেট করে দিতে হবে।

- TTL (Time To Live): ক্যাশ সেভ করার সময় একটি মেয়াদ সেট করে দেওয়া (যেমন ৫ মিনিট)। ৫ মিনিট পর ক্যাশ অটো মুছে যাবে এবং ডাটাবেস থেকে নতুন ডাটা আসবে।

### ৪. প্রিজমা ও রেডিস দিয়ে কোড লজিক (Conceptual)

```ts
async getAvailableSlots(turfId: string, date: string) {
  const cacheKey = `slots:${turfId}:${date}`;

  // ১. রেডিসে চেক করো ডাটা আছে কি না
  const cachedSlots = await this.redis.get(cacheKey);
  if (cachedSlots) return JSON.parse(cachedSlots);

  // ২. না থাকলে DB থেকে আনো
  const slots = await this.prisma.slot.findMany({ where: { turfId, date } });

  // ৩. রেডিসে ৫ মিনিটের জন্য সেভ করে রাখো
  await this.redis.set(cacheKey, JSON.stringify(slots), 'EX', 300);

  return slots;
}
```

### ৫. কেন এটি গেম চেঞ্জার?

- Latency: ইউজার কয়েক মিলিসেকেন্ডের মধ্যে রেসপন্স পাবে।

- Cost: ডাটাবেসের ওপর চাপ কমলে আপনাকে দামি বা বড় সার্ভার কিনতে হবে না।

- User Experience: অ্যাপটি সুপার ফাস্ট মনে হবে।

> সারসংক্ষেপ: রেডিস ক্যাশ হলো আপনার দোকানের "ডিসপ্লে সেন্টার"। কাস্টমার আসলে আপনি বারবার গোডাউনে (DB) না গিয়ে ডিসপ্লে থেকেই জিনিস দেখিয়ে দেন। এতে সময় বাঁচে এবং গোডাউনের ওপর চাপ কমে।

## Payment RaceUser Pay

```text
⚠️ Bottleneck #4 — Payment Race
User pay করলো কিন্তু webhook আসেনি
→ Booking pending এ আটকে আছে
User দুইবার pay করলো → double charge
Solution: Idempotency key + webhook retry
```

পেমেন্ট গেটওয়ে ইন্টিগ্রেশনের সময় এই Race Condition এবং Webhook সমস্যাগুলো সবচেয়ে বেশি মাথাব্যথার কারণ হয়। আপনার ধরা এই Bottleneck-টি প্রফেশনাল পেমেন্ট সিস্টেমে খুবই ক্রুশিয়াল। চলুন এটি সহজভাবে বুঝে নেই:

### ১. সমস্যা ১: Webhook আসেনি (Missing Webhooks)

ইউজার পেমেন্ট সাকসেসফুল করার পর পেমেন্ট গেটওয়ে (যেমন: SSLCommerz, Stripe) আপনার সার্ভারে একটি সিগন্যাল পাঠায়, যাকে বলা হয় Webhook।

কেন আটকে যায়? আপনার সার্ভার ডাউন থাকতে পারে, নেটওয়ার্ক ফেইল করতে পারে, অথবা গেটওয়েতে সমস্যা হতে পারে। এর ফলে ইউজার টাকা দিলেও আপনার ডাটাবেসে বুকিং 'PENDING' ই থেকে যায়।

সমাধান (Webhook Retry): বেশিরভাগ গেটওয়েতে "Retry Policy" থাকে। অর্থাৎ আপনার সার্ভার থেকে 200 OK রেসপন্স না পাওয়া পর্যন্ত তারা কয়েকবার (যেমন ৫ মিনিট পর পর) ওই সিগন্যালটি পাঠাতে থাকে।

### ২. সমস্যা ২: Double Charge বা ডুপ্লিকেট বুকিং

ইউজার হয়তো পেমেন্ট বাটনে দুইবার ক্লিক করেছে অথবা পেমেন্ট সাকসেস হওয়ার পর পেজ রিফ্রেশ করেছে। এর ফলে একই বুকিংয়ের জন্য দুইবার পেমেন্ট প্রসেস হয়ে যেতে পারে।

### ৩. আসল সমাধান: Idempotency Key (আইডেমপোটেন্সি কী)

এটি পেমেন্ট সিস্টেমের একটি জাদুকরী কনসেপ্ট। Idempotency মানে হলো—আপনি একই অপারেশন যতবারই করুন না কেন, রেজাল্ট সবসময় একই থাকবে এবং নতুন কোনো পরিবর্তন হবে না।

এটি কীভাবে কাজ করে?

- যখন ইউজার পেমেন্ট রিকোয়েস্ট পাঠায়, আপনি একটি ইউনিক আইডি (যেমন: booking_123_abc) জেনারেট করে পেমেন্ট গেটওয়েতে পাঠান। একেই বলে Idempotency Key।

- যদি ইউজার ভুল করে আবার একই রিকোয়েস্ট পাঠায়, গেটওয়ে দেখবে যে এই booking_123_abc কী-টি অলরেডি একবার প্রসেস হয়েছে। তখন সে নতুন করে টাকা না কেটে পুরনো সাকসেস রেজাল্টটাই আবার পাঠিয়ে দিবে।

### ৪. প্র্যাকটিক্যাল ইমপ্লিমেন্টেশন স্টেপস:

- Unique Transaction ID: ডাটাবেসে বুকিং তৈরি করার সময়ই একটি ইউনিক transactionId জেনারেট করে রাখুন।

- Idempotency Key: গেটওয়ের API কল করার সময় এই আইডিটি হেডার বা বডিতে পাঠান।

- Webhook Handler: যখন Webhook আসবে, তখন ডাটাবেসে চেক করুন ওই transactionId-এর স্ট্যাটাস অলরেডি 'PAID' কি না। যদি 'PAID' থাকে, তবে আর কিছু করবেন না (এটি ডুপ্লিকেট পেমেন্ট রোধ করবে)।

### ৫. কেন এটি গুরুত্বপূর্ণ?

- Trust: ইউজার যদি টাকা দিয়েও বুকিং কনফার্ম না পায়, সে আপনার অ্যাপ আর ব্যবহার করবে না।

- Refund Headache: ডাবল চার্জ হলে রিফান্ড করাটা অনেক ঝামেলার কাজ এবং এতে চার্জ কাটা যায়।

> সারসংক্ষেপ: Webhook Retry নিশ্চিত করে যে ডাটা হারাবে না, আর Idempotency Key নিশ্চিত করে যে একই কাজ দুইবার হবে না।

## Redis SPOF

```text
⚠️ Bottleneck #5 — Redis SPOF
Redis down হলে সব cache miss
Booking lock কাজ করে না
→ Queue job হারিয়ে যায়
Solution: Redis Sentinel / Cluster
```

### ১. সমস্যা: কেন রেডিস ডাউন হওয়া মানেই বিপদ?

আপনার সিস্টেমে রেডিস শুধু ক্যাশ হিসেবে নয়, বরং Locking এবং Queue Management-এর জন্য ব্যবহৃত হচ্ছে।

- Booking Lock ফেইল করবে: যদি দুইজন ইউজার একসাথে একই স্লট বুক করতে চায়, তখন রেডিস ডাউন থাকলে RedisLockService কাজ করবে না। ফলে Double Booking হয়ে যাবে।

- Queue Job হারিয়ে যাওয়া: পেমেন্ট ভেরিফিকেশন বা ইমেইল পাঠানোর মতো কাজগুলো যদি BullMQ (যা রেডিস ব্যবহার করে) দিয়ে করেন, তবে রেডিস ডাউন হলে ওই সব ডাটা হারিয়ে যেতে পারে।

- DB Crash: ক্যাশ না থাকলে সব ট্রাফিক সরাসরি ডাটাবেসে যাবে (Cache Stampede), ফলে ডাটাবেসও ডাউন হয়ে যেতে পারে।

### ২. সমাধান ১: Redis Sentinel (হাই এভেইল্যাবিলিটি)

Sentinel হলো অনেকটা রেডিসের জন্য একজন "বডিগার্ড" বা "মনিটর"।

এখানে একটি মেইন রেডিস (Master) থাকে এবং এক বা একাধিক কপি (Replica) থাকে।

সেন্টিনেল সবসময় চেক করে মাস্টার রেডিস বেঁচে আছে কি না।

যদি মাস্টার ডাউন হয়ে যায়, সেন্টিনেল সাথে সাথে একটি রেপ্লিকাকে নতুন "মাস্টার" বানিয়ে দেয়। আপনার অ্যাপ তখন নতুন মাস্টারের সাথে কথা বলা শুরু করে।

কার জন্য: ছোট থেকে মাঝারি স্কেলের অ্যাপের জন্য যেখানে ডাটা লস কমানো মূল লক্ষ্য।

### ৩. সমাধান ২: Redis Cluster (স্কেলিং + হাই এভেইল্যাবিলিটি)

যখন আপনার ডাটা এবং ট্রাফিক অনেক বেশি হয়ে যায়, তখন একটি মাত্র রেডিস সার্ভার সব লোড নিতে পারে না। Cluster তখন সমাধান দেয়।

এটি ডাটাকে ভাগ করে অনেকগুলো রেডিস নোডে (Nodes) ছড়িয়ে দেয়।

যদি একটি নোড ডাউন হয়, অন্য নোডগুলো কাজ চালিয়ে নেয়।

কার জন্য: অনেক বড় সিস্টেমের জন্য যেখানে প্রচুর ক্যাশ ডাটা হ্যান্ডেল করতে হয়।

### ৪. আপনার কোডে এর প্রভাব কী?

আপনি যখন আপনার TurfService-এ রেডিস কল করছেন:

```ts
await this.redis.delByPattern(`turf:list:*`);
```

যদি রেডিস ডাউন থাকে, এই কোডটি এরর দিবে এবং আপনার পুরো API ক্রাশ করবে। তাই কোড লেভেলে আমাদের Graceful Degradation বা এরর হ্যান্ডলিং রাখতে হয়:

```ts
try {
  await this.redis.delByPattern(`turf:list:*`);
} catch (error) {
  this.logger.error('Redis is down, but continuing without cache clearing');
}
```

### ৫. সারসংক্ষেপ (The Takeaway)

- Single Redis: ল্যাব বা ছোট প্রজেক্টের জন্য ঠিক আছে।

- Redis Sentinel: প্রোডাকশন অ্যাপের জন্য মাস্ট, যাতে রেডিস মরলেও সিস্টেম না মরে।

- Redis Cluster: যখন ইউজার সংখ্যা লাখে পৌঁছাবে।

> সহজ কথা: আপনার সিস্টেমের "মেমোরি" (Redis) যদি চলে যায়, তবে সিস্টেম যেন "কোমায়" না চলে যায়। Sentinel বা Cluster ব্যবহার করা মানে হলো ব্রেইনের একটা অংশ কাজ না করলে অন্য অংশ দিয়ে কাজ চালিয়ে নেওয়া।

## Missing Index

```text
⚠️ Bottleneck #6 — Missing Index
Slot table তে লাখো row হলে
date+turfId দিয়ে search slow হয়
Full table scan হয় → 500ms+ latency
Solution: Composite index on (turfId, date)
```

### ১. সমস্যা: Full Table Scan কী?

যখন আপনি ডাটাবেসকে বলেন, "অমুক তারিখের আর অমুক টার্ফের স্লটগুলো দাও", তখন ডাটাবেস যদি ওই কলামগুলোতে কোনো ইনডেক্স না পায়, সে একদম প্রথম সারি (Row) থেকে শেষ সারি পর্যন্ত প্রতিটা ডাটা চেক করে।

- ১,০০০ রো: খুব দ্রুত হবে।

- ১,০০,০০০ (১ লাখ) রো: ডাটাবেস হাঁপিয়ে উঠবে। একেই বলে Full Table Scan।

ফলাফল: যেখানে ৫-১০ মিলিসেকেন্ডে রেজাল্ট আসার কথা, সেখানে ৫০০ মিলিসেকেন্ড বা তার বেশি সময় লাগবে। ইউজার দেখবে পেজ লোড হতে অনেক দেরি হচ্ছে।

### ২. সমাধান: Composite Index (কম্পোজিট ইনডেক্স)

আপনার কোডে আপনি প্রায়ই turfId এবং date একসাথে ব্যবহার করে স্লট খুঁজবেন। তাই আলাদা আলাদা ইনডেক্স না করে একটি Composite Index তৈরি করা বুদ্ধিমানের কাজ। এটি অনেকটা বইয়ের শেষের Index Page-এর মতো, যা আপনাকে সরাসরি সঠিক পাতায় নিয়ে যাবে।

কেন Composite Index?

যদি আপনি শুধু turfId-এ ইনডেক্স করেন, ডাটাবেস টার্ফ খুঁজে পাবে ঠিকই, কিন্তু তারিখ খুঁজতে তাকে আবার অনেকগুলো রো চেক করতে হবে। কিন্তু (turfId, date) একসাথে ইনডেক্স করলে সে একবারে নির্দিষ্ট টার্ফের নির্দিষ্ট তারিখের স্লটে পৌঁছে যাবে।

### ৩. Prisma-তে এটি কীভাবে করবেন?

আপনার schema.prisma ফাইলে স্লট মডেলে নিচের মতো করে ইনডেক্স ডিফাইন করতে পারেন:

```js
model Slot {
  id        String   @id @default(uuid())
  turfId    String
  date      DateTime
  startTime String
  endTime   String

  // এখানে কম্পোজিট ইনডেক্স সেট করা হচ্ছে
  @@index([turfId, date])
}
```

বোনাস টিপ: যেহেতু আপনার সিস্টেমে একই টার্ফের একই সময়ে দুইটা স্লট হতে পারবে না, তাই আপনি চাইলে @@unique ও ব্যবহার করতে পারেন, যা অটোমেটিক ইনডেক্স হিসেবেও কাজ করবে:

```js
@@unique([turfId, date, startTime])
```

### ৪. ইনডেক্স করার পর কী পরিবর্তন আসবে?

| মেজারমেন্ট | ইনডেক্স ছাড়া | ইনডেক্স সহ |
| --- | --- | --- |
| কুয়েরি মেথড | Full Table Scan (পুরো টেবিল খোঁজা) | Index Seek (সরাসরি টার্গেটে যাওয়া) |
| পারফরম্যান্স | ডাটা বাড়লে স্লো হতে থাকে। | লাখ লাখ ডাটাতেও গতি কমে না। |
| Latency | ৫০০ms+ | ২ms - ১০ms |

### ৫. সতর্কবার্তা: ইনডেক্স মানেই কি সব সমাধান?

না! মনে রাখবেন, ইনডেক্স কুয়েরি ফাস্ট করে কিন্তু ডাটা Insert/Update করার সময় কিছুটা স্লো করে দেয়। কারণ প্রতিবার ডাটা সেভ করার সময় ডাটাবেসকে তার "ইনডেক্স ম্যাপটিও" আপডেট করতে হয়। তাই শুধু প্রয়োজনীয় কলামগুলোতেই ইনডেক্স দেওয়া উচিত।

> সারসংক্ষেপ: আপনার স্লট টেবিলে turfId এবং date এর ওপর ইনডেক্স দেওয়া মানে হলো আপনার সিস্টেমকে কয়েকশ গুণ বেশি ফাস্ট করে দেওয়া। এটি স্কেলেবিলিটির জন্য কোনো "অপশন" নয়, এটি একটি "মাস্ট"।
